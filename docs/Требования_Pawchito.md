# PAWCHITO — требования

**Версия 1.1 · 12.10.2026** — изменения в [журнале решений](Решения_Pawchito.md). Детали поведения — в [бизнес-правилах](Бизнес-правила_Pawchito.md), термины — в [глоссарии](Глоссарий_Pawchito.md).

## 1. Анализ

- **Проблема:** данные о здоровье питомца разбросаны, владелец забывает дозы и прививки, запись — по телефону.
- **Решение:** единая медкарта. Владелец ведёт историю и записывается к врачу, клиника вносит итог приёма и дополняет данные питомца, система сама создаёт дела по курсу и уведомляет участников на сайте. Диагнозы не ставит.
- **Роли:** владелец, клиника (аккаунт для администраторов клиники; у врача своего входа нет), администратор системы.
- **Входит:** питомцы, здоровье и дневник, запись к врачу, кабинет клиники, итог приёма, фото питомца от клиники, дела, календарь, уведомления на сайте, восстановление доступа, админка.
- **Не входит:** диагностика, оплата, чат, уведомления по email / push / Telegram, вход врача, вложения (кроме одного фото питомца), мобильное приложение.
- **Версии:** MVP — первый релиз, этапы 1–12 роадмапа; расширенная — после релиза, этап 13.
- **Решения:**
  - архивирование вместо удаления;
  - отпуск — флаг `on_vacation`;
  - слот — 30 минут в часы работы клиники;
  - access- и refresh-токены;
  - уведомления — на сайте, опросом раз в 60 секунд;
  - итог приёма после сохранения не редактируется.

**Риски**

| Риск | Мера |
|---|---|
| фронт и бэк разойдутся | контракт `openapi.json`, CI |
| не хватит времени | этапы по фичам; расширенная версия — после релиза MVP; при нехватке времени команда переносит в расширенную следующие требования |
| утечка токена | access-токен на 15 минут в памяти; refresh-токен в httpOnly-cookie с ротацией и отзывом |
| персональные данные в фото | пережатие на сервере, удаление EXIF |
| одно и то же называют по-разному | глоссарий; новый термин — сначала в глоссарий |

## 3. Системные требования

- **Безопасность:**
  - пароли, коды восстановления и временные пароли — Argon2;
  - access-токен — JWT на 15 минут, фронт хранит его только в памяти;
  - refresh-токен — на 30 дней в httpOnly-cookie, с ротацией; в БД хранится только хеш;
  - токены отзываются при выходе, смене пароля и блокировке;
  - HTTPS;
  - доступ и активность пользователя проверяются на сервере на каждом запросе;
  - число попыток входа и восстановления ограничено.
- **Надёжность:** целостность на уровне БД; итог приёма — одна транзакция; ежедневный бэкап БД и фото; медицинские данные физически не удаляются.
- **Файлы:** только фото питомца — JPEG / PNG / WebP до 5 МБ; на сервере хранится WebP до 1024 px без метаданных, в томе Docker.
- **Логи:** Redis Stream, хранение 14 дней; без паролей, токенов, кодов восстановления и медданных.
- **Скорость:** ответ API ≤ 500 мс, кроме загрузки фото.
- **Уведомления:** клиент обновляет их не реже раза в 60 секунд, без WebSocket.
- **Удобство:** русский интерфейс; адаптив: интерфейс владельца — от 360 px, кабинет клиники и админка — от 768 px.
- **Сопровождаемость:** слои бэкенда, линтеры и тесты в CI, актуальный `openapi.json`, схема БД — только миграциями Alembic, термины — по глоссарию.
- **Развёртывание:** `docker compose up`.
- **Сервер:** Linux VPS, 2 vCPU, 2 ГБ RAM, Docker, домен; PostgreSQL и Redis — в контейнерах.
- **Клиент:** актуальные Chrome, Firefox, Edge, Safari.

## 4. Несистемные требования

- Команда из 4 человек: back, front, devops.
- Работа по роадмапу, фронт и бэк параллельно.
- Git: ветка на задачу, PR с ревью, зелёный CI, без пушей в `main`.
- Задачи — в GitHub Projects.
- Схема БД меняется миграциями Alembic через Пугно, API — через контракт.
- Требования меняются через PR в `docs/` с записью в журнал решений.
- Платные ресурсы — только VPS и домен.
- В репозитории нет реальных персональных данных.
